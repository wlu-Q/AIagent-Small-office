# 需求分析

把用户要解决的问题转成足够清晰、可验证的目标。按任务需要使用；可单独用于讨论、分析或检查已有需求，不要求固定阶段、前置方法或一轮一份文档。

## 输入与信息缺口

以用户原始要求、本次工作背景、相关项目资料和真实观察为输入。区分用户明确表达或认可的内容、历史事实、当前证据和自己的建议。任务背景里的 proposals 仍是未确认建议；历史验证不证明当前产物通过。

先通过已授权的读取和检索工具查明信息。只对无法自行查明且实质改变结果的歧义请求关键输入，不重复询问已明确的要求。PM 使用现有 ask_clarification 获取缺失信息；被委派员工把缺口和影响报告给 PM，由 PM 统一与用户沟通。权限不足时报告阻碍，不用澄清代替授权。

## 方法

1. 说明用户希望获得什么结果、为谁解决什么问题，保留原始限制和否定要求。
2. 对照当前项目事实识别差距。需要专业分析时，PM 可通过能力路由选择真实员工；只有实际调用 task 才启动员工。
3. 给出必要的范围、非目标、关键场景和验收条件。需求已清晰时直接使用现有内容，避免重新设计用户没有要求的功能。
4. 有多种可行解释时，说明差异、影响和建议；不能把自己的推荐当成用户已认可。
5. 根据当前目标决定直接回答、继续分析、委派工作或请求必要输入。无需等待固定的需求确认阶段。

## 按需输出与证据

简单任务输出清晰结论即可。复杂需求可整理目标、范围、限制、验收条件、待决问题和来源；仅在用户需要或工作确有必要时产出文档，由有写入权限的员工执行。

结论关联实际文件、用户消息或观察结果；未读取的代码、未执行的验证、未经认可的建议须如实标注。修改原有目标必须有用户依据，不因整理需求扩大范围。
