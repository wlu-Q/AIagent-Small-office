# 架构设计与分析

以当前实现和用户目标为依据，寻找足够简单、可落地的结构。可独立解释已有架构、评审方案或设计局部改动；不要求先做需求文档，也不强制进入实现。

## 输入与信息缺口

读取目标、限制、相关入口、调用者、接口和数据流；文档只是线索，代码与实际执行结果决定当前事实。先查明仓库可获取的信息。关键取舍确实阻塞工作时，PM 用 ask_clarification 获取输入；被委派员工向 PM 报告。不凭猜测编造接口或扩大权限。

## 方法

1. 沿真实调用链描述现有行为，明确本次需要改变的边界。仅解释架构的问题到此即可回答。
2. 先判断已有能力是否可复用，再比较必要的实现选项；结合依赖版本、复杂度和维护成本说明选择。
3. 对涉及的接口、输入输出、数据归属、失败与恢复路径给出具体说明。状态或记忆说明必须区分本次工作、长期知识和运行事实。
4. 有专业知识缺口时，PM 通过真实能力路由委派分析或方案审查；员工仅使用自己获准的工具。
5. 标明待确认假设、兼容性影响、风险和可执行验证。依据当前目标决定是否继续，不把设计结论视为派工许可或验收证据。

## 按需输出与证据

输出可为简短架构解释、方案比较、接口说明或设计文档。图和代码示例只在有助于理解时提供；需要创建交付文件时由具备写权限的员工执行。

引用实际入口、调用者和验证结果。明确区分当前实现与拟议修改，不把存在文件、模型自述或历史测试当成本次方案已经落地的证明。
