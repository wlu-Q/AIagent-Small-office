# 任务规划

把目标整理成必要且可执行的工作。计划是可修改的方法产物，不是服务端状态机，不要求先完成需求或架构阶段；简单问题无需强制列计划。

## 输入与信息缺口

使用当前目标、用户限制、本次共同背景、相关结果和员工能力事实。先查明已有信息；缺少会实质影响结果的关键输入时，PM 使用 ask_clarification，被委派员工向 PM 报告。无法获得所需能力或权限时说明阻碍，不虚构员工或用提问提升权限。

## 方法

1. 识别完成目标真正需要的工作，不按旧阶段机械补齐流程；分析、写作、实现、验证和审查按需要组合。
2. 对每项工作写清目标、相关上下文、必要文件、限制、依赖和验收条件；不要共享完整聊天或无关历史。
3. 尊重用户已指定员工。未指定时，PM 用能力路由取得真实 Employee ID，再通过 task 工具委派；候选查询本身不执行工作。普通员工不能继续委派。
4. 独立工作可以在各自任务目录并行；有前后依赖或接口依赖时安排顺序。按照运行时返回的任务成果引用核对版本，任务目录中的修改不等于已经集成或交付。
5. 根据工具结果或员工反馈更新剩余工作。员工声明完成后仍需核对产物与适合该目标的实际证据；未验证项、失败项和阻碍如实说明。
6. 目标可交付时汇总结论；目标未全部达成时报告实际范围和原因。用最终回答结束本次任务，不调用业务完成工具，不额外要求固定交付确认。

小范围任务默认一次委派同一员工完成修改、必要验证和其权限允许的发布，不机械拆成三个任务。出现具体风险、集成依赖、失败、版本变化、覆盖缺口或用户明确要求独立审查时，再安排相应员工与验证并说明原因。历史分工不自动沿用，“检查一下”不自动等于独立测试；不能为减少调用省略必要测试。

员工交接只需说明改了什么、验证覆盖与结果、实际发布状态、遗留问题及必要成果引用；系统已有的版本和执行证据不重复抄写。长日志使用可访问引用，接手按需读取片段。

## 按需输出与证据

计划可用简短文字、列表或现有待办工具维护；需要正式文档时由有写权限的员工创建。不要输出旧 Workflow 的阶段协议或把计划条目包装成已执行任务。

完成情况必须对应真实文件、工具结果和本次验证；任务背景中的建议及历史测试不能替代当前验收。

## 接续已有工作

接手先核对成果版本、已完成检查、可访问的报告和剩余问题；只传必要结果，不复制完整聊天与工具日志。用 `task.workspace_mode=continue` 接续原工作区，或用 `fork` 从已有基础分叉；传真实 `workspace_id`。多份成果通过 `publish_task_result(source_workspace_ids=...)` 合并，不默认复制重写。文件未变化且证据仍适用时，不无理由重做检查；修改后判断受影响的验证范围。

集中探测环境，复用项目现有依赖与测试入口。长命令通过 `powershell_read` 携带上次 `output_cursor` 和 `wait_ms` 等待新增结果，不为等待重新启动命令。测试脚本应传播失败退出码，不能用末尾成功输出掩盖断言失败。

预算或循环中止时，交接部分成果、停止原因和剩余验收。缺少版本验证记录不等于没有执行过检查；进程退出码为零也不等于所有测试通过。缺少证据说“未记录／无法确认”，不要断言“没有做过”。

已有项目沿用现有语言、框架及接口；新项目在委派说明中给出必要的共同技术栈、数据字段和接口约定。有共享基础依赖时先准备必要骨架，再并行独立模块；无依赖不强制串行。用户已说明员工正在做的任务不重复委派。合适员工忙碌或必要工具不足时报告用户，不把委派变成等待队列。
